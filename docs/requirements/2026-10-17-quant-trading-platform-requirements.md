# 量化交易平台需求文档（PRD）

> 文档版本：v0.5（架构调整：采用 TradingView Pine 回测 + webhook 下单 + Python 执行层，方案B：FastAPI+Redis+Worker）
> 创建日期：2026-10-17
> 文档所有者：用户本人
> 适用范围：个人量化交易工具，不涉及对外服务

---

## 1. 项目概述

### 1.1 项目定位

面向个人使用的加密货币量化交易平台，采用 **TradingView Pine 回测 + Python 执行层** 的混合架构：策略在 TradingView 上用 Pine Script 实现与回测，通过 alert webhook 推送信号到 Python 服务，Python 负责风控、下单、状态持久化、监控告警。Python 端额外保留回测引擎做交叉验证（双回测）。不对外提供服务，不需要多用户、注册、客服、合规等商业化能力。

### 1.2 项目目标

| 优先级 | 目标 | 衡量标准 |
|---|---|---|
| P0 | 从OKX稳定采集行情与历史数据 | 单次可拉取1年以上1H K线，无断线、无丢字段 |
| P0 | 在历史数据上完成策略回测，输出收益曲线与关键指标（双回测） | 夏普、最大回撤、胜率等指标齐全；与 TradingView Pine 回测结果偏离度可量化 |
| P0 | Python 端提供 webhook server 接收 TradingView alert | 5秒内响应；信号不丢失；重复信号被识别去重 |
| P1 | 在OKX模拟盘运行策略，验证策略与执行链路（本地脚本模拟 webhook） | 与回测结果偏离度可量化 |
| P1 | 在OKX实盘自动执行策略，接收 TradingView 真 webhook 信号，资金 < 1000 USDT | 7×24稳定运行，异常自动告警 |
| P2 | 实时监控账户、持仓、盈亏、风险指标 | 异常时通过邮件告警；监控进程心跳丢失可被发现 |

### 1.3 非目标（Non-Goals）

明确不在本期范围内：

- 不做Web UI界面（命令行优先；webhook server 是后端 API，不算 UI）
- 不做多用户系统、注册登录、权限管理
- 不做券商/股票/外汇市场接入
- 不做高频交易（HFT）级别的低延迟优化
- 不做策略商城、跟单、社区等社交功能
- 不自研回测引擎替代 TradingView Pine；Pine 是回测主战场，Python 回测仅做交叉验证

### 1.4 假设与依赖

**假设**：
- OKX API v5 接口在未来1年内基本稳定，无大版本破坏性变更
- OKX 模拟盘行情与实盘行情数据延迟在可接受范围（<1秒）
- 用户已持有OKX账户、通过KYC、并能创建API Key
- 用户将在M3启动前开通 TradingView Pro 账户（alert webhook 是 Pro 功能）
- 本地Mac可保持长时运行（模拟盘阶段）；M5 上 VPS 后稳定
- 加密货币市场流动性在未来1年不出现极端枯竭
- TradingView alert webhook 服务的可用性符合其 SLA（一般 > 99.5%）

**依赖**：
- 依赖OKX REST API与WebSocket服务的可用性
- 依赖Python 3.11+运行环境与pip生态
- 依赖OKX公开的市场数据接口（无需付费数据源）
- 依赖本地Mac或云服务器的稳定网络连接
- 依赖 TradingView alert webhook 服务
- 依赖 Redis 服务（M2 启动后；本地用 brew install，VPS 用包管理器）
- 依赖 systemd 或 supervisord 进程管理（M5 上 VPS 后）

**假设变更触发条件**：当任一假设被证伪时（如OKX发布v6、API限频大幅收紧），暂停当前开发并修订本PRD。

## 2. 用户与场景

### 2.1 用户画像

仅一人使用：会Python（中阶）、熟悉加密货币基本概念、计划用OKX作为主交易所、对量化交易有学习意愿但尚未实战。

### 2.2 核心使用场景

| 场景 | 描述 | 触发频率 |
|---|---|---|
| 数据采集 | 周期性拉取指定品种的历史K线、产品配置、资金费率，存本地 | 每日/每周 |
| 策略研究 | 在Jupyter或脚本中加载历史数据，编写策略，跑回测看结果 | 高频（开发期） |
| 模拟盘验证 | 将策略接入OKX模拟盘，观察实盘行情下的表现 | 每策略上线前 |
| 实盘执行 | 策略自动监控信号并下单，无需人工干预 | 7×24 |
| 风险监控 | 查看账户余额、持仓、未实现盈亏、最大回撤、撤单率 | 实时/按需 |

## 3. 功能需求

### 3.1 行情数据采集模块

**目标**：从OKX REST + WebSocket稳定获取行情数据并落盘。

| 编号 | 功能项 | 详细要求 |
|---|---|---|
| F1.1 | 历史K线下载 | 支持指定品种（现货/永续）、周期（1m/5m/15m/1H/4H/1D）、时间范围；自动分页（单次最多100根，循环拉取）；断点续传 |
| F1.2 | 实时行情订阅 | WebSocket订阅tickers/books/trades频道；自动重连；本地缓存最近N条 |
| F1.3 | 产品配置拉取 | 拉取OKX所有交易对的产品配置（instrument参数），含最小下单量、价格精度等；**注意：模拟盘与实盘的`instIdCode`不同，需分别独立拉取**；2026-09-30后USD现货已迁移为USDC，需更新`instId`列表 |
| F1.4 | 资金费率/持仓量 | 支持拉取永续合约资金费率历史与持仓量，供策略使用 |
| F1.5 | 数据存储 | K线落盘为parquet（按品种/周期分文件）；产品配置存JSON；保留原始返回字段，不做语义重命名 |
| F1.6 | 限频管理 | 按端点组分类限频（详见[OKX API速查](../reference/OKX_API_REFERENCE.md#4-限频策略)）：公开行情20req/2s per IP、账户10req/2s per UID、单下60/批下300/撤单60req/2s per UID；命中`50011`睡眠2秒重试；本地维护按端点组的令牌桶 |
| F1.7 | 数据完整性校验 | 下载完成后按时间戳校验K线连续性（应等于周期间隔）；发现缺失段自动补拉（最多3次）；重复时间戳去重（保留最新）；校验OHLC逻辑（high≥open、close、low） |
| F1.8 | 多品种数据对齐 | 提供按统一时间轴对齐多品种K线的工具；缺失行可配置填充策略（前值填充/NaN标记/插值）；对齐结果输出为多列DataFrame，供回测与ML使用 |

### 3.2 策略回测模块

**目标**：在历史数据上验证策略逻辑，输出可对比的绩效报告。策略在 TradingView Pine Script 中实现，Python 端做交叉验证（双回测）；策略源码同时维护 Pine 版本与 Python 副本，通过 git 管理。

| 编号 | 功能项 | 详细要求 |
|---|---|---|
| F2.1 | 策略接口规范 | Python 端策略基类：`on_bar(bar)`、`on_tick(tick)`、`on_trade(trade)`等回调；策略状态独立，可并行回测多品种；策略实现需与 Pine 版本逻辑严格对齐 |
| F2.2 | 回测引擎 | 事件驱动；按时间顺序回放历史K线/Tick；模拟成交（市价/限价）；手续费按OKX费率配置 |
| F2.3 | 成交模拟 | 市价单按下一根开盘价成交；限价单按价格穿透成交；考虑滑点（可配置） |
| F2.4 | 绩效指标 | 总收益率、年化、夏普、最大回撤、胜率、盈亏比、交易次数、平均持仓时长；可与 TradingView Pine 回测结果对比 |
| F2.5 | 回测报告 | 输出收益曲线、回撤曲线、持仓变化、交易明细的CSV/HTML；可对比多策略 |
| F2.6 | 参数寻优 | 支持网格搜索策略参数；结果按指标排序；禁止未来函数 |

### 3.3 模拟盘交易模块

**目标**：在OKX模拟盘上验证 webhook server + 风控 + 下单 + 持久化的完整执行链路；M3 阶段用本地脚本模拟 TradingView alert 推送 webhook。

| 编号 | 功能项 | 详细要求 |
|---|---|---|
| F3.1 | 模拟盘接入 | 使用OKX的`x-simulated-trading:1`请求头；与实盘共用同一套API封装 |
| F3.2 | Webhook server | FastAPI HTTP 端点接收 TV alert JSON；5秒内 ACK；解析失败入死信队列；信号去重（基于 alert message hash + TTL 5min） |
| F3.3 | 信号队列与执行 | Redis LIST 队列；worker 进程 BRPOP 消费；下单失败入死信队列并告警；worker 心跳每分钟一次 |
| F3.4 | 风控规则 | 单品种最大持仓比例、总仓位上限、单笔最大下单量、日亏损上限、连续亏损保护；信号在风控校验失败时拒绝下单 |
| F3.5 | 订单管理 | 下单/撤单/改单/批量操作；订单状态轮询；异常自动撤单 |
| F3.6 | 模拟盘报告 | 记录每笔订单、成交、盈亏；输出与回测同口径的绩效对比 |
| F3.7 | 状态持久化与崩溃恢复 | 每次下单/成交/持仓变化写入SQLite；进程重启时从最后检查点恢复（持仓、挂单、最近处理信号）；与交易所订单状态做reconciliation对账，发现本地与远端不一致时以远端为准并告警 |

### 3.4 实盘交易模块

**目标**：在OKX实盘自动执行策略，接收 TradingView 真 webhook 信号，资金 < 1000 USDT。

| 编号 | 功能项 | 详细要求 |
|---|---|---|
| F4.1 | 实盘接入 | 实盘API Key + Secret + Passphrase；**仅开启交易+读取权限，不开提币**；绑定IP |
| F4.2 | 真 webhook 接入 | TradingView alert 配置指向 VPS 公网 webhook 端点；alert JSON 含 `side`/`inst_id`/`order_type`/`strategy_id`（信号型）；多个 Pine 策略的 alert 通过 `strategy_id` 路由到不同风控参数集 |
| F4.3 | 仓位管理 | 单品种最大持仓比例、总仓位上限、单笔最大下单量等风控参数（与 F3.4 风控引擎复用） |
| F4.4 | 异常处理 | 网络异常重试3次后告警；订单状态不明时主动查询；余额不足时停止下单 |
| F4.5 | 紧急停止 | 一键停止所有策略并撤单的kill switch；异常时自动触发 |
| F4.6 | 操作审计 | 每笔下单/撤单的日志（时间、品种、价格、数量、策略ID、原因） |
| F4.7 | 状态持久化与崩溃恢复 | 每次策略状态变更（信号/下单/成交/持仓变化）写入SQLite；进程重启时从最后检查点恢复策略上下文（持仓、挂单、上次信号时间）；与交易所订单状态做reconciliation对账，发现本地与远端不一致时以远端为准并告警 |
| F4.8 | 多进程编排 | VPS 上用 systemd 管 3 个进程：FastAPI server、worker、monitor；任一进程崩溃自动重启；重启时先做 reconciliation 再启动 |

### 3.5 账户/持仓监控模块

**目标**：实时了解账户与持仓状态，异常及时告警。

| 编号 | 功能项 | 详细要求 |
|---|---|---|
| F5.1 | 账户快照 | 余额、可用、冻结、未实现盈亏、保证金占用率 |
| F5.2 | 持仓快照 | 各品种持仓数量、方向、开仓均价、未实现盈亏、杠杆 |
| F5.3 | 风险指标 | 总保证金率、最大回撤实时值、强平价距离、撤单率 |
| F5.4 | 告警 | 余额异常波动、保证金率低于阈值、连续亏损、API错误率超阈值、Redis 队列堆积 > 50 条、worker 心跳丢失 > 2 分钟、死信队列新增条目时告警 |
| F5.5 | 告警渠道 | 邮件（SMTP）；异常时发邮件给所有者邮箱；本地同时记日志 |
| F5.6 | 监控自身心跳 | 监控进程每分钟写一条心跳日志；每4小时发一封"存活"邮件；若连续5分钟无心跳判定监控进程已死，下次启动时告警 |

## 4. 非功能需求

### 4.1 性能

| 项 | 要求 |
|---|---|
| 单次历史K线下载 | 1年1H数据（约8760根）< 60秒 |
| 回测速度 | 1年1H数据 + 单策略 < 5秒 |
| 实盘策略响应 | 信号到下单 < 2秒 |
| WebSocket重连 | < 5秒 |

### 4.2 可靠性

- 网络异常：所有HTTP请求重试3次，指数退避
- 进程崩溃：实盘模块必须可重启后恢复（订单状态自检）
- 数据完整性：历史数据落盘前校验字段完整性，缺失则重拉

### 4.3 可维护性

- 模块边界清晰：行情/回测/交易/监控各自独立，通过明确接口通信
- 配置与代码分离：所有API Key、品种列表、风控参数走配置文件
- 日志规范：统一格式，按模块+日期分文件，保留30天

### 4.4 安全性

- API Key 仅存于本地配置文件（`~/.okx/`或项目`config/`），**永不入库、永不打印到日志**
- 实盘Key仅开交易权限，绑定本机出口IP
- 模拟盘Key与实盘Key分离，配置文件切换
- **子账户策略**：实盘使用OKX子账户而非主账户；子账户仅转入本期实盘所需资金（<1000 USDT）；即使Key泄露，影响范围限于子账户余额；主账户资产隔离
- **凭证轮换**：API Key每90天定期轮换；轮换流程为：创建新Key→配置文件切换→验证模拟盘→禁用旧Key→删除旧Key；泄露时立即禁用+走轮换流程

### 4.5 部署

- 初期：Mac本地，开发与模拟盘
- 后期：部署到云服务器（VPS），实盘7×24运行；部署方式待定（systemd / Docker）

### 4.6 时间口径

| 项 | 规范 |
|---|---|
| 内部存储与计算 | 一律UTC（ISO 8601带`Z`后缀，毫秒精度） |
| K线时间戳 | 开盘时间（与OKX返回一致） |
| 本地展示 | 用户可读层才转UTC+8（Mac本地时区） |
| 签名时间戳 | OKX要求ISO 8601 UTC毫秒，与服务端时差<30秒 |
| 日志时间 | UTC，日志中明示时区，避免歧义 |
| 回测时间轴 | UTC；展示收益曲线时按需转本地 |
| 跨日聚合 | 按"UTC日"切分，必要时为策略提供"交易所在时区日"工具方法 |

### 4.7 边界场景处理

| 场景 | 检测 | 处理 |
|---|---|---|
| OKX维护期/停机 | HTTP 5xx连续3次、或特定错误码`50001`/`50013`等 | 暂停所有策略；每30秒探测一次；恢复后先做reconciliation再启动 |
| 极端行情 | 单根K线振幅（high-low)/open > 阈值（默认10%） | 触发风控：暂停该品种策略N分钟；发送告警邮件；恢复需人工确认 |
| 部分成交 | 订单状态为`partially_filled` | 按累计成交量推进策略状态机；剩余挂单可配置（继续等待/改价/撤单） |
| 撤单回报未到 | 撤单请求发出后N秒（默认5秒）仍未收到回报 | 主动查询订单状态；若仍为`new`/`partially_filled`则视为撤单失败，重试 |
| 订单状态不明 | 本地状态与远端查询结果不一致 | 以远端为准；本地状态纠正；记录discrepancy日志；连续3次不一致触发告警 |
| 余额不足 | 下单前预检余额；下单返回`51008` | 停止该策略下单；尝试撤掉其他挂单释放保证金；告警 |
| API Key失效 | 返回`50111`/`50113` | 立即停止所有策略；发送紧急告警邮件；等待人工更换Key |
| 时钟漂移 | 客户端与服务端时差>15秒 | 自动校时；校时失败则停止下单 |
| USD/USDC现货迁移 | 2026-09-30生效：`Crypto-USD`现货已下线 | `instId`列表必须用`Crypto-USDC`；若需USD计价显式传`tradeQuoteCcy=USD`；启动时拉取最新instruments验证 |
| post-only订单state行为 | 2026-08-20生效：挂单失败只推`state: canceled` | 策略状态机不能假设先收到`live`再收到`canceled`；收到`canceled`即视为挂单失败 |
| RPI订单低于最小名义金额 | SPOT<500 / FUT<2000 / SWAP<5000 USD | 返回`54051`；调整下单金额或换非RPI类型 |
| WebSocket产品频道增量推送 | 2026-09-30生效：instruments频道由全量改增量 | 本地维护产品缓存，按`instId`更新；不能假设每次推送是全量 |

## 5. 技术选型（建议，待评审）

### 5.1 已选型清单（核心）

| 层 | 选型 | 理由 |
|---|---|---|
| 语言 | Python 3.11+ | 你熟悉；量化生态成熟 |
| HTTP | `httpx` | 简单可靠，同步+异步双支持，未来扩展空间 |
| WebSocket | `websockets` 自封装 | 代码全可见，避开 SDK 黑盒 |
| 数据处理 | `pandas` + `polars`（大数据量） | pandas生态广，polars快 |
| 数据存储 | parquet（K线）+ SQLite（订单/持仓/信号/死信）+ JSON（配置） | 简单、无外部依赖 |
| 回测引擎 | 自研轻量框架（Python 副本与 Pine 双回测） | 灵活可控；避开backtrader的复杂度 |
| Webhook server | `FastAPI` + `uvicorn` | 标准现代 Python Web 框架；自动 OpenAPI 文档；同步端点简单 |
| 信号队列 | `Redis`（LIST + BRPOP）+ 死信队列 | 个人项目 LIST 简单可靠；Stream 过度 |
| 信号去重 | Redis SET + `hash(signal_json)` + TTL 5min | TV 网络异常会重发 alert |
| 进程管理 | 本地手动；M5 后 `systemd` 管 3 进程（FastAPI/worker/monitor） | 简单优先 |

### 5.2 后续按需引入（待M3/M5阶段评估）

以下技术在当前阶段不强制选型，待对应里程碑启动时再决定，避免过度设计：

| 用途 | 候选技术 | 何时决定 |
|---|---|---|
| 机器学习（M2之后） | `scikit-learn`、`xgboost`、必要时`pytorch` | M2结束、启动ML策略时 |
| 监控告警（M4） | 邮件SMTP（`yagmail`/`aiosmtplib`）；可选Prometheus+Grafana | M4启动时 |
| 任务调度（M3+） | `apscheduler`（本地轻量）/ `Celery`（上云后） | M3启动时 |
| 进程监控（M6上云） | `supervisor` / `systemd` / `Docker` | M5结束、上云前 |
| 配置管理 | `pydantic-settings` / `python-dotenv` / `tomllib` | M1时决定 |
| 日志 | 标准库`logging` + `loguru`（可选） | M1时决定 |
| 单元测试 | `pytest` + `pytest-asyncio` | M1时决定 |
| 数据校验 | `pydantic` v2 | M1时决定 |
| 异步支持 | `asyncio` + `aiohttp`（必要时） | M3/M5需要并发时再决定 |
| 时区处理 | `pendulum` 或标准库`zoneinfo` | M1时决定 |

> 原则：M1阶段优先用最简方案，能不引入就不引入；每个新里程碑启动时回顾此表，按需补充。

## 8. 风险与开放问题

### 8.1 已识别风险

| 风险 | 等级 | 应对 |
|---|---|---|
| OKX API变更或限频策略调整 | 中 | 客户端封装层隔离；监控错误码 |
| 实盘亏损超出预期 | 高 | 严格风控参数 + kill switch + 小资金起步 |
| 时间戳与服务端偏差导致签名失败 | 中 | 客户端定期校时（±30秒内） |
| 机器学习策略过拟合 | 高 | 严格样本切分 + 走查测试 + 与简单策略对比 |
| 本地断电/断网导致策略中断 | 中 | M6上云解决；M5前小资金试错 |
| Redis 服务故障导致队列不可用 | 中 | worker BRPOP 失败时进入退避重试 + 告警；FastAPI 端 LPUSH 失败时返回 503 让 TV 重试 |
| TradingView alert webhook 重发或丢失 | 中 | 信号去重（hash+TTL）；死信队列；状态持久化让重启可恢复 |
| Pine 与 Python 策略逻辑不一致 | 高 | 策略实现需代码评审；双回测结果偏离 > 5% 时禁止上实盘 |
| worker 进程崩溃未处理信号丢失 | 中 | BRPOP 后先 LPUSH 到 inflight 队列再处理；进程重启时优先消费 inflight |
| TV Pro 账户未开通阻塞 M5 | 中 | M3 用本地脚本模拟 alert 推迟 TV 依赖；M5 启动前完成开通 |

### 8.2 已确认的设计决策

| 问题 | 用户决策 | 影响 |
|---|---|---|
| M1作为第一步 | 同意 | 立即启动数据底座模块开发 |
| 项目结构 | 暂时认可，后期如有变动再调整 | 按第6节骨架推进，保留调整空间 |
| 技术选型 | 核心清单认可；其余技术按需补充 | 已扩展第5.2节"后续按需引入"清单 |
| 告警渠道 | 邮件（SMTP） | 已更新F5.5 |
| 机器学习策略 | 一步一步来，按里程碑推进 | ML策略排在M2回测引擎之后，单独排期，不在M1范围 |
| 前端策略开发与回测方案 | TradingView Pine Script + Python 双回测 | 策略源码同时维护 Pine 与 Python 两份；Pine 是主回测；Python 做交叉验证 |
| Webhook 推送方案 | 信号型 webhook（仅 side/inst_id/order_type/strategy_id） | Python 端负责风控、下单、仓位管理；TV 只发信号 |
| Webhook 部署位置 | M3 模拟盘本地；M5 实盘 VPS | M3 不依赖 TV Pro；M5 启动前开通 |
| Webhook 架构方案 | 方案 B：FastAPI + Redis 队列 + worker 进程 | 多进程异步处理；信号去重；死信队列；状态持久化；M5 systemd 编排 3 进程 |
